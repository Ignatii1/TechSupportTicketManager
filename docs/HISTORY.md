### 2026-10-07 — v0.13.0: выгрузка всех заявок, какие видит учётная запись
- Пользователь: ему дали права на чтение специально для массовой выгрузки, чтобы потом анализировать; спросил, не мешает
  ли программа выбрать все заявки, в том числе где он не исполнитель. Разобрались по коду: поиск не мешал (пустые условия —
  все заявки, что видит учётная запись), а выгрузка мешала: потолок 2000 (`MaxLimit`), 11 страниц списка, весь список в
  памяти, одна плоская папка, один `_index.md` на всё (перечитывал каждый файл), `ReadExisting` читал заголовок каждого файла.
- Решения. (1) «Не больше, заявок» — `0` значит все, сверху потолка нет: любое число было бы выдумкой; вместо потолка — вопрос
  от 2000 заявок (часы работы и тысячи запросов к общему серверу). (2) Потоково: страница списка → сразу файлы по ней →
  следующая страница; в памяти страница, словарь «номер → имя файла» (без чтения файлов — читаются только заголовки заявок
  из списка) и множество уже виденных номеров. (3) Список — по `Created asc, Id asc`: дата создания не меняется, а по
  изменению тронутая за часы выгрузки заявка прыгнула бы наверх, куда чтение уже не вернётся. Сортировка из примера
  документации (стр. 15), на живом сервере не проверена — страховка: ответ 4xx на первой странице → то же по `Changed desc`
  (с заметкой), список не по возрастанию создания или повторяющий страницу — в заметке/стоп. (4) Продолжение — то же
  правило «не менялась — пропуск» (формат и `changed` в файле), поэтому ни файла состояния, ни режима «продолжить»: остановка,
  вылет, сон компьютера, сбой сети — следующий запуск идёт по готовому только страницами списка. (5) Папки по месяцам
  создания, оглавление в каждой и общее в корне: сотни тысяч файлов в одной папке не поднимут Проводник и Obsidian;
  оглавления переписываются только у тронутых за выгрузку месяцев; плоские файлы 0.10–0.12 переезжают сами по `created` из
  файла, без запросов. (6) Повторы сбойного запроса (2, 5, 15 с) только для сбоев, которые проходят сами (сеть, срок, 5xx,
  408, 429); логин (401), доступ, «нет такой» не повторяются. Выключатель на всю выгрузку: 401; 30 сбоев сети подряд без
  единой удачи; 25 отказов (404/403) при нуле записанных; 10 ошибок записи подряд — иначе выгрузка часами долбила бы лежащий
  сервер или полный диск. Счётчики раздельные: иначе «ни одна не читается» срабатывало раньше «сервер лёг». (7) Срок
  запроса стал свой у каждого: страница списка с описаниями и точным счётом по сотням тысяч заявок может не уложиться в 10 с,
  а общий `HttpClient.Timeout` это не позволял (теперь 60 с на страницу списка). (8) Размер страницы остался 200 (на
  живом сервере известно, что отвечает); 2000 разрешены документацией, но ответ толще, а сотни лишних запросов рядом с
  запросами на каждую заявку ничего не стоят.

  «сервер не прислал» (у закрытых потерялась бы). `SetThreadExecutionState` против сна не стал: состояние привязано к потоку, а
  выгрузка прыгает по потокам пула — нужен был бы отдельный поток-сторож ради случая, который выключатель и продолжение уже
  переживают; в вопросе и README сказано «не давайте компьютеру уснуть». CSV-индекса нет (предложить, если понадобится для анализа).

  всё сразу и порядок «страница списка → файлы → следующая страница» (по журналу запросов); остановка на запросе №70 и на

### 2026-10-03 — v0.12.0: поиск любых заявок по условиям, просмотр, буфер, выгрузка
- Пользователь: скоро будет доступ на чтение ко всем заявкам — «развить поиск и скачивание»: не только мои, а любые, по
  всем способам, что даёт API, с сочетанием условий; смотреть найденное и при желании скачивать, чтобы отдать агенту.
  Раньше я просил у него сырые ответы, потому что документация из контейнера недоступна; теперь он прислал
  `IntraService_API_v5_51.pdf` — имена параметров взяты из него (стр. 14-20, 33-37, 53-61), а не угаданы. Остальные сырые
  ответы (`api/task?pagesize=2`, `api/filter?resource=task`) он пришлёт позже — образцы потом в SelfCheck.
- Решения. (1) Одно окно «Поиск заявок» вместо двух (поиск и выгрузка были про одно и то же): условия → список → просмотр
  → буфер/файлы. (2) Условия — все, что есть у списка заявок в документации; пропущены те, что нужны редко или требуют
  справочника с обязательным сервисом (группа исполнителей, категории, приоритеты — в компании не заполняются): их закрывает
  «Сохранённый фильтр» — отбор собирают в веб-интерфейсе один раз. (3) Сотрудников ищем по части фамилии через
  `api/user?search=`: один — берём; несколько (до 10) — ищем по всем и пишем над списком, по кому; ни одного или больше
  десяти — ошибка с просьбой уточнить: молча расширять или сужать поиск нельзя. (4) По умолчанию ищем и в архивных,
  неактуальных сервисах (`archive=true&inactive=true`): без этого сервер их заявки молча не отдаёт, а базе знаний нужна
  вся история. (5) Сервис — вместе с вложенными (по `Path`, номера уходят списком), чтобы условие не зависело от того,
  берёт ли сервер вложенные сам. (6) Общее число — с `count=all`: без него, по документации, сервер считает до тысячи, и
  «найдено 1000» ничего бы не значило. (7) Просмотр — тот самый Markdown, что уйдёт в файл и в буфер: человек видит ровно то,
  что получит агент; «Копировать» — до 30 заявок за раз (больше в чат всё равно не влезет). (8) «Выгрузить найденные» ждёт
  нового поиска, если условия поменяли после него (выгрузка идёт по условиям, давшим список на экране).
